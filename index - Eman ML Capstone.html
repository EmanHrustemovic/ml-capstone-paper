Refresh / Content Opportunity Scoring: Flagging Declining Pages Before They Lose Visibility

Eman Hrustemović · August 2026
Abstract

This study asks whether page-level search decline can be flagged early enough for a content team to act, using only features available before the outcome is known. We built a page-level dataset from FlyRank's search warehouse (March 2026), labeling pages as declining when their average search position worsened between the first and second half of the month. A Logistic Regression model, trained on five early-window features, was compared against a hand-written CTR-vs-position baseline rule under both a random split and a stricter client-grouped split. The model reached Precision@50 of 0.96 under both splits (baseline: 0.70), with an AUC of 0.649 under the honest client-grouped evaluation — a real, though modest, lift over the baseline's 0.544 AUC. The resulting ranked queue, with a reason code explaining each flag, is intended as decision-support for content teams, not an automated publishing pipeline.

Introduction

Content teams can't manually review every page every month. This work supports one concrete decision: which pages should be prioritized for refresh, given limited editorial time? The unit of analysis is one page, aggregated from daily warehouse data within a single month. The output is a ranked queue with a reason code per page — not an automated action, but a starting point for human review.

Machine learning helps here because the underlying signals (search position, click-through rate, content staleness, page volume) interact in ways no single hand-written rule captured as well as a model that weighs them jointly — as shown directly in the results below.

Data

Data used: fact_content_daily_performance (month=2026-03, ~9.84M rows) and dim_content, from the FlyRank internship Hugging Face warehouse release.

What was excluded, and why

  • Rows where GSC data was not available — only ~37% of rows have usable search data; excluded rather than imputed.
  • Any late-window (post-decision-point) fields, since they are label-derived. A deliberate leakage test confirmed this: adding a late-window feature pushed model AUC from ~0.68 to 0.9999 — proof the feature was effectively the label in disguise. It was removed.
  • Client identifiers are used only for grouping in validation (see Methodology), never as a model feature.
  • The dataset's final month (June 2026) was used only to test query mechanics early on, never for label or feature development, since it is the natural outcome window for any past-to-future label.
No client names, domains, URLs, or private queries appear anywhere in this project — all identifiers are salted hashes provided by the warehouse release itself.

Methodology

Label

is_declining_label — 1 if a page's average search position in the second half of March is worse than in the first half, else 0. Base rate: 52.0% positive class.

Features

impr_early, avg_position_early, ctr_early, word_count, days_since_update — all computable at the decision point, none derived from the outcome window.

Baseline

A single-signal heuristic: flag a page if its observed CTR is significantly below the expected CTR for its position bucket. Before building it, two candidate signals were tested directly:

  • Staleness — OPPOSITE of expected: the freshest bucket (0–30 days) had the highest decline rate (54.1%, n=140,458), not the lowest. Dropped as a rule driver.
  • CTR-vs-position — CONFIRMED: a clean, monotonic drop from 0.346% CTR (top 3 positions) to 0.128% CTR (position 20+). Used as the baseline's foundation.

Model

Logistic Regression, chosen for interpretability and because its probability outputs rank cleanly for a Precision@K task. Random Forest was trained as a comparison point.

Validation design

Two splits were compared: an initial random 70/30 stratified split, and a stricter client-grouped split (confirmed zero client overlap between train and test) — the more honest evaluation, since the goal is generalizing across clients, not memorizing client-specific patterns.

Precision@50 held steady (0.960) under the stricter client-grouped split — the top-50 ranked predictions don't depend on client-specific leakage. AUC dropped modestly (0.675 → 0.649) versus the random split, suggesting a small amount of the original AUC was inflated by the model learning client-level patterns. With a base rate of 52.0%, Precision@50 = 0.96 remains a substantial, measured lift over chance-level precision.

Error analysis

In the top-50 ranked list, only 2 of 50 were false positives. Both shared an identical, anomalous profile: avg_position_early near 0 (GSC positions are 1-indexed, so this is likely a data aggregation artifact) and a negative days_since_update — a data quality issue, not a silent model failure.

Interpretation

Logistic Regression coefficients: avg_position_early (-0.048, strongest) shows a floor effect — pages already ranking poorly have less room to decline further. days_since_update (-0.0018) is weakly negative, consistent with the OPPOSITE staleness finding above — more time since update was not associated with higher decline risk in this data. ctr_early (+0.009) and impr_early/word_count (near zero) contributed comparatively little.

Limitations & Honest Framing

  • Short baseline window: the label compares two 15-day halves of one month — this can't fully distinguish a real ranking decline from normal search volatility.
  • Data availability: only ~37% of rows had usable GSC data; the model is trained on a non-random subset of total traffic.
  • Single month: all results come from one month (March 2026) and have not yet been validated against a different month or live data.
  • Observational, not causal: all findings describe associations in this dataset, not causal mechanisms. No claim is made about predicting or reverse-engineering how Google's ranking algorithm works.
  • Decision-support only: Precision@50 of 0.96 means the top of the queue is reliable, not perfect — nothing here should be auto-published or used client-facing without human review.

How an editor would use this tomorrow: open the ranked queue, start from the top, and treat each row's reason code as a starting hypothesis, not a verdict — verify the specific issue before spending editorial effort.

What should never be automated: auto-publishing content changes based on this score alone; auto-deleting or de-indexing flagged pages; using this score as the sole input to any client-facing report without human review.
